# Flavour reward maps (v1)

FlavourRewardMapV1 is a small, offline score-table format for repeatable culinary portfolio evaluation. It separates **candidate generation** from **selection**: a scorer looks up the frozen score for a three-item portfolio, and applies hard constraints before returning the score. It does not call a model, fetch a service, or assert that a map represents universal human taste.

## Current artifact and limitations

`shared/evals/flavour-reward-map-v1.json` contains 50 tasks (17 substitution, 17 pairing, 16 constraint) and 2,800 frozen three-of-eight portfolio scores. The artifact is explicitly a **synthetic QA fixture pack**, generated by `shared/scripts/build-flavour-reward-map.js` from task-specific seeded item, pairwise, and trio utilities. It contains no third-party dataset/checkpoint, proprietary weights, user data, or network-derived data. Its values exercise the schema, hashing, ranking, explanations, and hard-block path; they are **not culinary recommendations, learned preferences, or evidence of agreement with cooks**.

The artifact source and license metadata travel with the content. Before using a released Epicure checkpoint or a Seasoned co-occurrence overlay, add its exact source, version, license, and reproducible rebuild method to the artifact and this document. Do not add weights or corpus-derived data unless the license permits redistribution. A changed task catalog, source, or score table must produce a new `artifactHash` and map identity.

## Artifact contract

- Top level: `schemaVersion`, `mapId`, `artifactHash`, `source`, `families`, `generation`, and `tasks`.
- Families are `substitution`, `pairing`, and `constraint`.
- Each task has a unique `taskId`, family, prompt, exactly eight unique `{ id, label }` candidates, `k: 3`, and a score for every one of the 56 unordered three-item portfolios. Portfolio keys are JSON arrays of lexically sorted candidate IDs.
- `constraints.hardBlockedIds` is optional. A portfolio containing any such ID scores **0**, irrespective of its frozen table value, and is not assigned a rank. This is an additional gate, not a replacement for the allergen graph or process-safety checks.
- Scores are integers from 0 through 100. `bestScore` is the best score among constraint-valid portfolios. `rank` is one-based with lexical portfolio-key tie-breaking; it is `null` for a hard-blocked selection.
- `artifactHash` is `sha256:<lowercase hex digest>` over canonical JSON for the complete artifact **without** the `artifactHash` property. Object keys sort recursively, arrays keep their order, and no other values are normalized.

## Offline API

```js
import { readFile } from 'node:fs/promises'
import {
  createFlavourRewardScorer,
  verifyFlavourRewardMapIntegrity,
} from '../shared/flavour-reward-map.js'

const map = JSON.parse(await readFile('shared/evals/flavour-reward-map-v1.json', 'utf8'))
const integrity = await verifyFlavourRewardMapIntegrity(map)
if (!integrity.valid) throw new Error(integrity.errors.join('; '))

const scorer = createFlavourRewardScorer(map)
const result = scorer.scorePortfolio('sesame-free-noodles', ['ginger', 'lime', 'tahini'])
// result: score0to100, bestScore, rank, explainTopDiffs[], and blockedReason when gated
```

`scorePortfolio(taskIdOrInlineTask, chosenIds)` is synchronous after scorer construction. Explanations compare the requested selection with up to three highest-scoring valid alternatives and expose only ingredient-ID additions/removals and score deltas. Malformed task references, duplicate selections, wrong portfolio size, and IDs outside the candidate set throw; hard-block violations return score zero rather than throwing.

## Commands and rollout

From `recipe-generation-worker/`:

```sh
npm run eval:flavour-maps
```

This local/CI check is deterministic and offline; it verifies the content hash, all three families, the 50-task minimum, all 56 rows per task, a frozen-score lookup, and an adversarial hard-block override. Rebuild the synthetic artifact from `shared/` with `node scripts/build-flavour-reward-map.js`.

The product flag key is `flavour_reward_map_v1` and defaults to **off** in the app's Flaggly bootstrap. The eval command does not consult the product flag. No generation/adaptation consumer, Opik span, or product-facing score UI is connected by this foundation slice. In particular, never send raw pantry data to reward-map telemetry; any future optional span should contain map ID/hash and non-sensitive task/selection IDs only.

## Non-claims and next steps

A high score means only “high under this exact versioned map.” It is not a universal taste rating, a safety certification, nutrition or medical advice, or proof that a cook will prefer the choice. Hard allergen and process-safety gates remain authoritative and must run before any future ranker displays a candidate.

The current synthetic data makes the verifier fully executable without pretending that a licensed culinary checkpoint is already integrated. A follow-up data slice should replace or supplement the QA pack with a redistributable public checkpoint or a reproducible, permitted co-occurrence overlay, then evaluate map calibration separately from verifier correctness. CI currently validates the artifact on changes to the map, generation/adaptation handlers, and quality-bar; richer regression baselines belong to the continuous-evaluation upgrade.
